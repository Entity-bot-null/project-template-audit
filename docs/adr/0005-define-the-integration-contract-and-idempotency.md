# 0005. Define the integration contract in Zod, with idempotent events and a gapless sequence

- **Status:** Proposed
- **Date:** 2026-10-14
- **Deciders:** Audit Hub maintainers

## Context

Audit Hub receives events from many applications, each running several versions during a rollout,
and from devices that queue events offline for days. The audit module this replaces lost events
in silence when a field did not validate, and left fields empty because nothing said which ones an
action needed. The contract therefore has to do several things:

- describe every event exactly, for machines (validation) and for people (review);
- let each application declare its actions with their category, severity, details and personal
  or sensitive fields;
- survive at-least-once delivery without duplicates;
- make a lost or suppressed event visible;
- evolve without breaking the applications that have not updated yet.

The template's conventions apply: the contract is generated, committed and drift-checked; JSON
fields are `camelCase`; every input is a Zod schema.

## Options

1. **A hand-written JSON Schema as the source**, validated with `ajv` and turned into TypeScript
   types with `json-schema-to-typescript`. It is language-neutral. On the other hand, there would
   be a second validator next to Zod, two code generators, and error messages that don't follow
   the template's `path: message` format.
2. **Zod schemas as the source** (`packages/audit-contract`), with the JSON Schema generated by
   `z.toJSONSchema()` (Zod 4.6.5, target draft 2020-12) and committed. There is one validator, the
   same one the API uses for everything, and the types are inferred. The JSON Schema stays the
   published, versioned artifact for anyone outside TypeScript.
3. **Protobuf or Avro**, which give compact frames and a schema registry. They add a toolchain
   and a binary wire format, and they don't fit an HTTP+JSON API.

For the per-application sequence (`sourceSeq`), there were three ways to assign the number:

- **A database sequence** at insert time. It gives a number at once, but PostgreSQL sequences are
  not transactional: every rolled-back business transaction leaves a hole, and gap detection
  would raise false alarms all day.
- **A counter row incremented when the forwarder takes rows from the queue.** It is
  transactional, so a rollback gives the numbers back, and it numbers rows in commit order. A
  transaction that commits late simply gets a later number.
- **No sequence**, deduplicating by id only. It cannot tell a lost event from one that never
  existed.

## Decision

Option 2, with these rules:

- **Idempotency key:** `eventId`, a UUIDv7 generated once at the origin. Audit Hub stores it under
  `UNIQUE (app_id, event_id)` and answers `duplicate` to a repeat. The connectors keep their row
  until Audit Hub answers, so delivery is at least once and storage exactly once.
- **Sequence:** the connector's forwarder assigns `sourceSeq` from a counter row
  (`audit_outbox_state`), inside the transaction where it claims unsequenced rows. The numbers
  are gapless and follow commit order. The counter row also carries a `sequenceEpoch`. A database
  restore or a deliberate reset starts a new epoch, which an admin must acknowledge in Audit Hub.
  **Every answer consumes its number:** a rejected event, or a duplicate arriving with a new
  number, is written to `ingest_exceptions`. A gap therefore always means an event that never
  arrived, never one that was refused.
- **Per-event results:** a batch is never rejected because of one event. Identity fields reject
  only their event. A bad optional field is dropped and listed in `droppedFields`. A string that
  is too long is truncated and listed in `truncatedFields`. Retryable rejections, for now only an
  unknown catalog version, keep their row in the queue.
- **Catalog:** each action declares its category, default severity, description, source
  (`server`, `client` or `both`), tags from a closed vocabulary the rules understand,
  `userVisible`, and flat field specs for `details` and `change`, each field marked `personal` or
  `sensitive`. Field specs have no regex, no `$ref` and no nesting. Audit Hub compiles them to
  Zod, and a compromised application cannot publish a pattern that blocks the ingestion
  (ReDoS). An action can never move to a category with a shorter minimum retention. Devices may
  only emit actions whose source is `client` or `both`.
- **Wire format:** `camelCase`, as docs/api-conventions.md requires (the brief listed the fields in
  `snake_case`; the database keeps `snake_case`). Every string is bounded. Ids follow a closed
  pattern without `@`, so an email cannot pass for an id.
- **Versions:** `contractVersion` (equal to the event's `schemaVersion`) is an integer that goes
  up only on a breaking change. Audit Hub accepts the current and the previous one, announces its
  supported versions and deprecations in the heartbeat answer, and records the connector name and
  version of every request.

## Consequences

- The contract package is the only source of the event's shape for Audit Hub, both connectors and
  the generated JSON Schema. A drift spec fails when the committed JSON Schema differs from what
  Zod produces.
- Sequencing adds one small transaction per forwarder cycle. One counter row serializes
  sequencing (not sending) across the application's instances, which is cheap at audit volumes.
- A database restore of the application without a new epoch would reuse numbers. Audit Hub
  answers `sequence_conflict`, which is alerted, and the runbook resets the epoch.
- Devices cannot pick their sequence numbers: the application's backend assigns them when it
  queues their events. A device that is offline for a week shows up as late events, not as a gap.
- We would know this was wrong if catalogs regularly needed nested or pattern-validated details
  (then extend the field-spec vocabulary, never accept arbitrary JSON Schema), or if the
  sequence's serialization showed up as forwarder lag.
